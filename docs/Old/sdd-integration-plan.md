# Seamless SDD Integration Plan — fx-to-dotnet Extension

**Status**: Superseded — see banner above.  
**Date**: April 24, 2026  
**Scope**: fx-to-dotnet extension hook commands only (no spec-kit core changes)

---

## Executive Summary

The fx-to-dotnet extension already has 5 SDD hooks covering the full spec-kit lifecycle (`after_specify` → `after_plan` → `after_tasks` → `before_implement` → `after_implement`). A deep review of both the spec-kit core framework and the fx-to-dotnet extension reveals **6 integration gaps** that prevent a truly seamless experience when a user runs the standard `specify → plan → tasks → implement` workflow on a .NET Framework migration project. All fixes are within the extension's hook command files — no modifications to spec-kit core are required.

---

## Current State

### How It Works Today

```
speckit.specify  ──after_specify──►  specify-hook
                                     │ Detects migration context
                                     │ Runs project detection
                                     │ Appends "Migration Context Detected" to spec.md
                                     ▼
speckit.plan     ──after_plan─────►  plan-hook
                                     │ Runs assess + plan
                                     │ Appends "Migration Assessment Summary" to spec.md
                                     │ Appends ".NET Migration Plan" to plan.md
                                     ▼
speckit.tasks    ──after_tasks────►  tasks-hook
                                     │ Generates [MIG]-tagged tasks
                                     │ Appends ".NET Framework Migration" section to tasks.md
                                     ▼
speckit.implement──before_implement─► implement-hook
                                     │ Executes [MIG] tasks via FxToNet commands
                                     │ Marks tasks [X] on completion
                                     ▼
                 ──after_implement──► verify-hook
                                     │ Audits task completion
                                     │ Runs solution build
                                     │ Writes .specify/migration/completion.md
```

### What Goes Wrong

The hooks execute correctly in isolation, but the **data handoff between spec-kit core commands and extension hooks** has friction points that produce duplicate work, incorrect ordering, and missing context.

---

## Gap Analysis

### Gap 1: Duplicate Task Generation from Migration Plan

| | |
|---|---|
| **Problem** | `plan-hook` appends a detailed `## .NET Migration Plan` to plan.md with actionable phase details (SDK conversion candidates, package update plan, etc.). When `speckit.tasks` runs, the core AI reads ALL of plan.md and generates its own migration-related tasks from this section. Then `tasks-hook` adds the proper `[MIG]` tasks — creating duplicates. |
| **Root Cause** | The core tasks command has no concept of "extension-managed" sections in plan.md. It treats every actionable section as input for task generation. |
| **Impact** | Users see duplicate tasks: one set generated by core (vague, without `[MIG]` tags or command dispatching) and one set from the extension (properly tagged with FxToNet command references). |

### Gap 2: Migration Tasks Positioned at End of tasks.md

| | |
|---|---|
| **Problem** | `tasks-hook` appends `## .NET Framework Migration` at the bottom of tasks.md. But migration is prerequisite infrastructure — SDK conversion and package updates MUST complete before user-story implementation tasks can use the modernized codebase. |
| **Root Cause** | The hook uses a simple append strategy rather than inserting at the correct position in the task hierarchy. |
| **Impact** | The core implement agent may attempt user-story tasks before migration is complete, leading to build failures on the old framework. |

### Gap 3: No Dependency Linking Between [MIG] and User-Story Tasks

| | |
|---|---|
| **Problem** | User-story tasks may depend on .NET 10 APIs or migrated project references, but nothing in tasks.md declares that `[MIG]` tasks block `[US*]` tasks. |
| **Root Cause** | The core tasks format supports dependency annotations (`depends on T###`) but `tasks-hook` doesn't generate cross-phase dependencies. |
| **Impact** | The implement agent has no explicit signal that migration must complete first. Parallel execution strategies could attempt user-story work prematurely. |

### Gap 4: Spec Enrichment Lacks AI Guidance Markers

| | |
|---|---|
| **Problem** | `specify-hook` adds `## Migration Context Detected` and `plan-hook` adds `## Migration Assessment Summary` to spec.md. The core `plan` and `tasks` commands read spec.md and may try to generate redundant planning or task items from these informational sections. |
| **Root Cause** | Core commands are AI agents that process ALL spec.md content as actionable requirements. There is no marker distinguishing extension-managed reference sections from user requirements. |
| **Impact** | Redundant planning effort and potential for conflicting migration strategies between core-generated and extension-generated content. |

### Gap 5: No Post-Migration Context Handoff

| | |
|---|---|
| **Problem** | `implement-hook` (before_implement) executes all `[MIG]` tasks and marks them `[X]`, but provides no summary of what codebase changes were made. The core implement agent starts processing remaining tasks with no awareness of the transformations that just occurred (new TFMs, renamed namespaces, removed packages, etc.). |
| **Root Cause** | The implement-hook completion step only reports task counts, then returns control silently. |
| **Impact** | The core implement agent may use outdated API patterns, reference removed packages, or miss new framework capabilities when implementing user-story tasks. |

### Gap 6: verify-hook Doesn't Update SDD Artifacts

| | |
|---|---|
| **Problem** | `verify-hook` writes `.specify/migration/completion.md` but doesn't update the SDD plan.md or tasks.md. The SDD artifacts don't reflect migration completion or build verification status. |
| **Root Cause** | The verify-hook rules state "this hook is informational" — it only writes to the `.specify/migration/` directory. |
| **Impact** | The SDD artifacts (plan.md, tasks.md) remain incomplete — they show migration as planned/tasked but not as verified. Anyone reviewing the SDD artifacts gets an incomplete picture. |

## Proposed Changes

### Phase A: Plan-Hook — Extension-Managed Directives

**File**: `fx-to-dotnet/commands/plan-hook/plan-hook.md`  
**Fixes**: Gap 1, Gap 3, Gap 4

#### Change 1: Add extension-managed directive to migration plan section

In step 9 (Enrich SDD Plan), when appending `## .NET Migration Plan` to plan.md, prepend an AI-directive blockquote:

```markdown
## .NET Migration Plan

> **Extension-managed phases** — The migration phases below are planned and executed
> by the `fx-to-dotnet` extension. Do NOT generate tasks from this section during
> `speckit.tasks`; migration tasks are produced automatically by the extension's
> `after_tasks` hook with `[MIG]` tags. Treat this section as reference context only.
```

This prevents the core tasks command from generating duplicate migration tasks.

#### Change 2: Add migration dependency cross-reference

At the end of the migration plan section in plan.md, add:

```markdown
### Migration Dependencies

All user-story implementation tasks depend on completion of the migration phases above.
The `[MIG]`-tagged tasks generated by the `after_tasks` hook must complete before
user-story `[US*]` tasks begin. The `before_implement` hook enforces this ordering
by executing all `[MIG]` tasks first.
```

#### Change 7: Add extension-managed note to assessment summary in spec.md

In step 5 (Enrich Spec), when appending `## Migration Assessment Summary` to spec.md, include:

```markdown
## Migration Assessment Summary

> **Extension-managed** — This section is maintained by the `fx-to-dotnet` extension.
> Migration planning, task generation, and execution are handled by extension hooks
> during the SDD lifecycle. Do not generate separate migration tasks from this content.
```

### Phase B: Tasks-Hook — Correct Positioning and Dependencies

**File**: `fx-to-dotnet/commands/tasks-hook/tasks-hook.md`  
**Fixes**: Gap 1, Gap 2, Gap 3

#### Change 3: Insert migration tasks before user stories

Change step 6 (Write Tasks) from appending at the end to inserting AFTER the last Foundational/Setup phase and BEFORE the first User Story phase. The insertion logic:

1. Scan tasks.md for the first `## Phase *: *User Story*` or `## Phase *: *[Title]* (P1)` heading
2. Insert `## .NET Framework Migration` section immediately before that heading
3. Renumber subsequent phase headings to maintain sequential numbering
4. If no user-story phases are found, append at the end (fallback to current behavior)

Resulting task structure:
```
## Phase 1: Setup
## Phase 2: Foundational
## Phase 3: .NET Framework Migration    ← inserted here
  ### SDK Normalization (Layer-by-Layer)
  ### Package Compatibility
  ### Multitarget Migration
  ### Web Migration
## Phase 4: User Story 1 - [Title] (P1) 🎯 MVP    ← renumbered
## Phase 5: User Story 2 - [Title] (P2)             ← renumbered
## Phase N: Polish & Cross-Cutting Concerns          ← renumbered
```

#### Change 4: Add dependency annotations

After writing migration tasks, add a `### Dependencies` subsection:

```markdown
### Dependencies

All `[US*]` user-story tasks depend on completion of all `[MIG]` migration tasks.
The .NET Framework migration phase must complete before user-story implementation
begins, as user-story code targets the migrated framework ({targetFramework}).
```

#### Change 5: Duplicate detection and cleanup

Before writing `[MIG]` tasks, scan existing tasks.md for non-`[MIG]` tasks that reference migration concepts. Specifically look for tasks containing any of:
- "SDK conversion", "SDK-style", "convert to SDK"
- "package update", "package compatibility", "NuGet update"
- "multitarget", "multi-target", "target framework"
- "framework migration", ".NET migration", "migrate to .NET"

If found:
1. Remove the duplicate tasks from tasks.md
2. Adjust task numbering for any tasks that followed the removed ones
3. Include a note in the output: "Removed {N} duplicate migration-related tasks that were generated by the core tasks command. These are replaced by the `[MIG]`-tagged tasks below."

In step 4 (Completion), before returning control to core implement, append a `## Migration Execution Summary` section to the SDD plan.md:

```markdown
## Migration Execution Summary

> This summary was generated by the `fx-to-dotnet` `before_implement` hook after
> completing all `[MIG]` tasks. Use this context when implementing remaining tasks.

### Projects Converted to SDK-Style

|---------|---------|---------|
| {project} | {oldTfm} | {targetFramework} |
```

```markdown

> All projects now target the new framework. Implement remaining tasks using
> modern .NET APIs and patterns. See `## Migration Execution Summary` in plan.md
> for details of changes made.
```

## Design Decisions

| Decision | Rationale |
|----------|-----------|
| All changes within fx-to-dotnet extension only | Keeps spec-kit core generic; extension-managed markers are a convention any extension can adopt |
| Blockquote (`>`) format for AI directives | Visually distinct in rendered Markdown; AI agents can parse reliably; doesn't break document structure |
| Migration tasks as a dedicated phase (not merged into Foundational) | Preserves the extension's identity in the task list; makes `[MIG]` scope clear; easier to track/audit |
| Duplicate detection via keyword matching | Robust against varied phrasing in core-generated tasks; conservative — only removes clear migration duplicates |
| Migration execution summary written to plan.md | Maximum visibility to the core implement agent, which loads plan.md as primary context |
| verify-hook updates are additive (append-only) | No risk of corrupting existing SDD content; safe for re-runs |
| `[MIG]` tag convention preserved | Already established in v0.2.0; no breaking changes to existing task format |

---

## Risk Assessment

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Core tasks command ignores blockquote directives and generates duplicates anyway | Low — AI agents reliably parse explicit "Do NOT generate tasks" instructions | Defense-in-depth: tasks-hook dedup (Change 5) removes any duplicates that slip through |
| Phase renumbering breaks task references | Low — task IDs (`T###`) are independent of phase numbers | Task ID references remain stable; only phase headings change |
| Migration execution summary is too verbose for plan.md | Medium | Keep summary to key facts (tables); full details remain in `.specify/migration/` state files |
| Dedup keyword matching removes legitimate user-story tasks | Very low — keywords are specific to migration concepts | Only scan for tasks NOT tagged `[MIG]` that contain migration-specific terms |

## Version Impact

These changes are additive and backward-compatible. Recommended version bump: **0.3.0 → 0.4.0** (minor) since they add new behavior to existing hooks without breaking the existing API or hook contracts.
